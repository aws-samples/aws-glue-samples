# Failure classification

Find the symptom, name the class to the customer, and apply the fix. Every class also lists the
command that confirms it. The job runs at the same Ray 2.4.0 / Python 3.9 and the same dependency
versions as on Glue, so these are environment and configuration failures, not code-port failures.

## Build time

| Class | Symptom | Cause | Fix |
|---|---|---|---|
| <a id="source-built"></a>`SOURCE-BUILT` (not a failure) | `resolve-deps.sh` prints `SOURCE-BUILT` with a wheel name | No wheel existed for Python 3.9 / arm64, so the sdist was built from source, as Glue did. The built wheel is saved to `wheels/` and installed in the image | None. Note the package in the report |
| <a id="no-wheel"></a>`NO-WHEEL` | `resolve-deps.sh`: `No matching distribution found for X==v` / `from versions: none` | No wheel **and** no buildable sdist for Python 3.9 / arm64. Usually an x86-only package, or one that needs a newer Python | Glue ran arm64 Python 3.9, so a package with no arm64 build there could not have installed on Glue either: check the job's run history. If it never ran successfully with this pin, tell the user and ask whether to drop the pin (never drop it silently). Moving to an amd64 image and node pool is the user's choice, not parity |
| <a id="sdist-build-failed"></a>`SDIST-BUILD-FAILED` | `resolve-deps.sh`: `Failed building wheel for X` / `subprocess-exited-with-error` | No wheel exists, and the sdist does not build in the base image (missing compiler or headers) | `resolve-deps.sh` retries without build isolation. If it still fails, confirm the Glue job used the package; add the missing build tools to the resolve image only if Glue built it the same way |
| `TRANSITIVE-PIN` | `No matching distribution found for Y<...` with `(from X)` in the log | A pinned package `X` requires a `Y` with no wheel for Python 3.9 / arm64 | Resolve with the customer: a different `X`, or a compatible `Y`. Re-run the import check |
| `RESOLVER-CONFLICT` | `ResolutionImpossible`, `conflicting dependencies` | The job's `--pip-install` requirements conflict with each other (or with `ray`, which stays at the base image's version) | Show the conflict and ask the customer which pin to move. Never drop a pin without asking |
| `INDEX-UNREACHABLE` | `Could not fetch URL`, `Connection` | Private index, or no egress from the build host | Run the build where the index is reachable, and pass `PIP_EXTRA="--index-url ..."` |
| `IMPORT-FAIL` | `import-check.txt` shows `FAIL x` | A module the script imports isn't installed (a dynamic dependency, or one the Glue job got another way) | Add it to `requirements.in` and re-resolve |
| `APT-K8S-REPO` | `apt-get update` fails (`apt.kubernetes.io` / `NO_PUBKEY`) | The Ray 2.4 base image lists the retired Kubernetes apt repository | `rm -f /etc/apt/sources.list.d/kubernetes.list` before `apt-get update` (see the Dockerfile template) |
| `EXEC-FORMAT` | `exec format error` | The image architecture doesn't match the node or the build host | Build natively on the target architecture: locally on an arm64 machine, or in CodeBuild on arm64 (Step 6). No emulation. Check with `docker image inspect --format '{{.Architecture}}'` |

## Scheduling and startup

| Class | Symptom | Cause | Fix |
|---|---|---|---|
| `API-UNREACHABLE` | `eksctl` or `kubectl` fails with `dial tcp <ip>:443: i/o timeout` right after the cluster is created | The cluster's public access CIDRs don't include the egress this machine uses for AWS endpoints. An `eksctl create cluster` that stops here has also skipped the add-ons it installs after the nodes, such as the CloudWatch Observability add-on | With the user's approval, add their egress range: `aws eks update-cluster-config --name <C> --resources-vpc-config endpointPublicAccess=true,endpointPrivateAccess=true,publicAccessCidrs=<list>`. Then `eksctl create addon -f cluster.yaml` installs the missing add-ons; check them with `aws eks list-addons --cluster-name <C>` |
| `POD-PENDING-SIZE` | Head or worker `Pending`, event `Insufficient memory/cpu` or `no instance type has enough resources`, or no NodeClaim. Often appears after a DaemonSet (logging/monitoring agent) is added to the nodes | Requests larger than node allocatable (64Gi on r7g.2xlarge doesn't fit) | Use the plan's 7 CPU / 54Gi, leave room for DaemonSets on the node, or use a larger instance. `kubectl describe pod`, `kubectl get nodeclaims` |
| `POD-PENDING-PLACEMENT` | `Pending` with `didn't match Pod's node affinity/selector` or `untolerated taint` | A selector or toleration doesn't match the NodePool or node group | Use the same `--capacity` / `--nodepool` / `--nodegroup` / `--toleration` values for rendering and for the cluster |
| `SUBMITTER-ARCH` | The submitter Job pod fails with `exec format error` while the Ray pods are fine | The submitter template had no arch selector and landed on an x86 node | `render_manifests.py` always sets `submitterPodTemplate.nodeSelector`. Don't drop it |
| `CAPACITY-QUOTA` | NodeClaims fail with `InsufficientInstanceCapacity` / `VcpuLimitExceeded` | EC2 On-Demand vCPU quota (replaces the Glue M-DPU quota) or AZ capacity | `aws service-quotas get-service-quota --service-code ec2 --quota-code L-1216C47A`. Request an increase, or allow more AZs or instance types |
| `IMAGE-PULL` | `ErrImagePull`, `toomanyrequests` | Docker Hub rate limit (pods behind NAT, or the build pulling the `rayproject/ray` base image, for example in CodeBuild), or no ECR permission | Run the job from the ECR image; the Auto Mode node role can pull from ECR in the same account. For the base image, log in to Docker Hub in the build, or mirror the base image into ECR |
| `KUBERAY-API-VERSION` | The autoscaler doesn't scale, or the operator logs errors about the API version | The Ray 2.4 autoscaler talks to `ray.io/v1alpha1`. KubeRay plans to stop serving it in 1.9, and v1-only fields can be pruned | Use a KubeRay release below 1.9 (`[KUBERAY_VERSION]` = 1.7.1). Keep the RayCluster spec to v1alpha1 fields (no top-level `labels`, group `resources`, or RayCluster `metadata`); the renderer already does |
| `DELETION-STRATEGY` | `kubectl create` rejects `deletionStrategy`/`deletionRules` (unknown field or validation error), or finished runs are never cleaned up | The KubeRay operator is older than 1.7, or its `RayJobDeletionPolicy` feature gate is off | Use KubeRay `[KUBERAY_VERSION]`, whose Helm chart enables the gate by default. Check the operator's `--feature-gates` argument: `kubectl -n kuberay-system get deploy kuberay-operator -o yaml` |

## Run time

| Class | Symptom | Cause | Fix |
|---|---|---|---|
| `ACCESS-DENIED` | `AccessDenied` / `403` from S3 in driver or task logs, naming `assumed-role/<pod role>/...` and `because no identity-based policy allows the <action> action` | The pod role is missing a policy of the Glue role, or a test-run location isn't covered | Name the missing action and ARN. Compare the role's policies with `manifests/iam/` (and `test-run/manifests/s3-policy.json` for a test run) |
| `ACCESS-DENIED-NODE-ROLE` | `AccessDenied` naming the **node** role instead of the pod role | IRSA isn't wired: the pod has no `eks.amazonaws.com/role-arn` ServiceAccount, so it fell back to the node role (blocked by IMDS hop limit 1 on node groups) | `kubectl -n NS get sa <SA> -o yaml` must show `eks.amazonaws.com/role-arn`; the role's trust must name `system:serviceaccount:<NS>:<SA>` |
| `ACCESS-DENIED-RESOURCE-GRANT` | `An error occurred (AccessDenied) when calling the GetObject operation: User: arn:aws:sts::<acct>:assumed-role/<pod role>/... is not authorized to perform: s3:GetObject on resource: "arn:aws:s3:::<bucket>/<key>" because no identity-based policy allows the s3:GetObject action` (or `(403) when calling the HeadObject operation: Forbidden`), for a location the Glue job could read | The Glue job's access came from the **bucket policy**, which names the Glue role and not the pod role (see `grants.md`) | The customer adds the pod role's ARN to that bucket policy statement (next to the Glue role). Takes effect within seconds |
| `ACCESS-DENIED-KMS-GRANT` | `... is not authorized to perform: kms:Decrypt on resource: arn:aws:kms:<region>:<acct>:key/<id> because no identity-based policy allows the kms:Decrypt action` when reading an S3 object | The object is encrypted with a KMS key whose **key policy** grants the Glue role, not the pod role (see `grants.md`) | The customer adds the pod role to that key policy statement (`kms:Decrypt`, and `kms:GenerateDataKey` for writes) |
| `ACCESS-DENIED-LAKE-FORMATION` | `An error occurred (AccessDeniedException) when calling the GetTable operation: Insufficient Lake Formation permission(s): Required Describe on <table>` (or another permission, operation and resource) | Lake Formation permissions were granted to the Glue role, not the pod role (see `grants.md`; a listing saved without all its pages misses some) | A data lake administrator, or a principal with the grant option, grants the same permissions to the pod role (`aws lakeformation grant-permissions --principal DataLakePrincipalIdentifier=<pod role ARN>`) |
| `ACCESS-DENIED-SOURCE-IP` | `... is not authorized to perform: s3:GetObject on resource: "arn:aws:s3:::<bucket>/<key>" with an explicit deny in a resource-based policy`, for a bucket whose policy allows only certain IP addresses (`aws:SourceIp`), even the NAT gateway's | S3 requests from the pods go through the VPC's S3 gateway endpoint, and such requests carry no `aws:SourceIp`, so an `aws:SourceIp` condition can't match them | Change the bucket policy's network condition to `aws:SourceVpce` (the gateway endpoint's ID) or `aws:SourceVpc`. NAT gateway IPs apply only to other public endpoints |
| `ACCESS-DENIED-BOUNDARY` | `AccessDenied` for a test-run location that `s3-policy.json` grants | The Glue role's permissions boundary, which the pod role has too, doesn't allow that location; a boundary caps inline grants | Choose test-run locations inside the boundary. Widening the boundary is the customer's security decision |
| `GLUE-CONDITION-DENY-GONE` | An object the Glue job was denied is now readable (or a Deny unexpectedly blocks everything) | A Deny on the Glue role was conditioned on `glue:CredentialIssuingService` or `glue:RoleAssumedBy`, which no request carries on EKS | The analyzer rewrites the statement as it applied on Glue (`W-IAM-GLUE-CONDITION`), and `manifests/iam/` holds the rewritten policy. Check that the pod role has that copy, not the original |
| `OOM` | Pod `OOMKilled`, or `RayOutOfMemoryError` / `OutOfMemoryError` | Object store + heap above the pod limit. `to_pandas()` on large data. Tasks without `memory=` | Confirm the object-store percentages map to the 54Gi pod limit, not 64. Raise the instance size if the job was tuned for Z.2X's full 64 GB |
| `SPILL-FAIL` | `Failed to spill objects` / smart_open errors | Spill bucket permissions, or `smart_open` missing from the image | Check `RAY_object_spilling_config`, the image packages, and the pod role's write access to the spill bucket. Fall back to local disk spilling on the 160Gi ephemeral volume |
| `HOME-OR-PATH` | `FileNotFoundError` / `PermissionError` on `/home/glue-ray-engine` or `/opt/amazon`, or `KeyError: 'HOME'` behaving differently | The script assumed the Glue runtime user, HOME or layout (analyzer `GLUE-PATH`) | Apply the analyzer's fix: derive paths from `os.environ['HOME']` / `tempfile`, or drop checks of Glue internals. This is a code change: propose it as a diff and apply it only with the user's approval (`SKILL.md` Step 3) |
| `ARGV` | The script reads no arguments, or `IndexError` on `sys.argv` | The script read `sys.argv` (analyzer `GLUE-ARGV`); on Glue arguments came as env vars, not argv | Read arguments from `os.environ`; the skill sets them. This is a code change: propose it as a diff and apply it only with the user's approval (`SKILL.md` Step 3) |
| `NODE-DISRUPTED` | Pods terminated mid-run (`Disrupted`, `Expired`, `Drifted`) | Karpenter consolidation, drift or expiry | Ray pods carry `karpenter.sh/do-not-disrupt: "true"`. The NodePool uses `WhenEmpty`. For spot, design for retries |
| `IDLE-SCALEDOWN` | Much slower than on Glue, or stalled: the autoscaler log shows `Terminating the node ... (idle)` during the run, then the driver logs `Attempting to recover ... lost objects` and `Total lineage size ... exceeds the limit`, and tasks stay `PENDING_ARGS_AVAIL` with no CPU in use | The autoscaler removed workers whose CPUs were idle (for example waiting on spilled-object restores or in a serial phase); the objects they held were lost. Glue's own controller managed the nodes, so the same job didn't lose workers there | Use the default idle timeout (600 s): re-render without a shorter `--idle-timeout-seconds`, or remove a short `--auto-scaling-executor-idle-timeout` from the plan's arguments (operator decision 20), and run again. End the stalled run with `kubectl -n NS delete rayjob <RAYJOB>` |
| `COLD-START` | Much slower than on Glue without any `Terminating the node ... (idle)`: workers join a minute or more after the job starts, the head spills heavily meanwhile, and later stages read spilled objects back | The job has no `--min-workers`, so it starts on the head alone while new nodes launch and pull the image (on Glue, workers joined within seconds) | Set `--min-workers` in the plan's arguments so workers are up before the script starts, raise the object-store percentages, or spill to local disk instead of S3 |
| `DEADLINE` | RayJob `Failed` with `DeadlineExceeded` | `activeDeadlineSeconds` (Glue Timeout) reached | Same as a Glue timeout: tune the job or raise the limit |

## Useful commands

Add `--context glue-ray-<C>` to each `kubectl` command (`SKILL.md` Step 7).

```bash
JOB=<glue job name, as rendered>; RAYJOB=<rayjob name, printed by kubectl create>
kubectl -n $NS get rayjob $RAYJOB -o jsonpath='{.status.jobStatus} {.status.jobDeploymentStatus} {.status.message}{"\n"}'
kubectl -n $NS logs job/$RAYJOB --tail=200                  # driver output; after the run, use the log pipeline
RC=$(kubectl -n $NS get rayjob $RAYJOB -o jsonpath='{.status.rayClusterName}')
kubectl -n $NS get pods -l ray.io/cluster=$RC -o wide          # head + workers of this run
kubectl -n $NS exec $(kubectl -n $NS get pod -l ray.io/cluster=$RC,ray.io/node-type=head -o name) -c ray-head -- ray status
kubectl -n $NS logs -l ray.io/cluster=$RC,ray.io/node-type=head -c autoscaler --tail=50
kubectl -n $NS port-forward svc/$RAYJOB-head-svc 8265:8265   # dashboard, during the run
# head/worker pod logs (kubectl logs <pod>) hold only Ray start-up output, not the job's prints
kubectl get nodeclaims; kubectl describe nodepool ray-z2x
```
