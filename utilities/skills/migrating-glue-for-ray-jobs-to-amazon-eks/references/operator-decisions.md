# Decisions the customer makes, and what each implies

The skill shows these at the review gate. **ASK** items have no safe default and need the customer's
answer. **DEFAULT** items use the stated choice unless the customer overrides it. The migration keeps
the Glue for Ray runtime version, so none of these is a version-upgrade choice.

| # | Decision | Default / ask | What it implies |
|---|---|---|---|
| 1 | New or existing EKS cluster | ASK | Existing: the skill checks the Kubernetes version, add-ons, capacity mode and OIDC provider (IRSA), and that any existing KubeRay operator is at least 1.7 and below 1.9, with the `RayJobDeletionPolicy` feature gate on, before using it. NetworkPolicy enforcement is the cluster owner's: the user confirms it (decision 13) |
| 2 | VPC, subnets, API endpoint access | ASK | Glue for Ray jobs ran with no customer VPC. EKS pods run in one, so they need an S3 gateway endpoint, NAT (or a PyPI mirror) for any runtime installs, and a private API endpoint or restricted CIDRs. The cluster template requires the CIDRs (`[OPERATOR_CIDR]`); they must include the machine running the migration |
| 3 | Capacity: EKS Auto Mode (Karpenter) or managed node group | DEFAULT Auto Mode with a dedicated arm64 NodePool | Auto Mode nodes follow Ray's autoscaler (one scaling layer). With a fixed-size node group, Ray scales into that pool; Cluster Autoscaler adds a second layer to tune. Self-managed nodes need the `eks.amazonaws.com/nodegroup` label for `--capacity nodegroup` |
| 4 | Architecture | DEFAULT arm64 (Graviton, Glue parity) | Native binaries in `--s3-py-modules` were built for aarch64 and keep working. amd64 (with an amd64 node pool) only if the customer chooses it: every dependency the Glue job installed had an arm64 build |
| 5 | Run model: ephemeral RayJob or long-lived RayCluster | DEFAULT ephemeral RayJob | Matches Glue's per-run cluster and isolation, with no idle cost. Each run has a cold start (node launch + 2–3 GB image pull: minutes). A job without `--min-workers` starts on the head alone while workers join; if it spills, it can run several times slower than on Glue (troubleshooting `COLD-START`). A shared long-lived cluster is warm but noisy and always billing |
| 6 | Dependencies | Baked into the image | The image holds the Glue runtime's package versions and the job's own, resolved once and reviewed, so every run uses the same versions as on Glue. It needs an image pipeline, and the customer now owns CVE patching of the image. Installing them at each start with a runtime env instead would resolve against the plain Ray image rather than Glue's package set, and is slow and needs PyPI egress, so the skill doesn't offer it |
| 7 | Code location: image or S3 `working_dir` | DEFAULT script and py_modules in the image, `--working-dir` kept as an S3 URI | The image is immutable: every run uses the code that was reviewed, and rolling back is a change of image tag. Ray could also fetch the `--s3-py-modules` zips at each start (runtime env `py_modules`, as Glue did), but then the zips can change between runs. S3 code deploys without an image rebuild |
| 8 | Emulate the Glue runtime contract, or refactor | DEFAULT emulate (env vars, `JOB_NAME` / `JOB_RUN_ID`, the min-workers floor, head-as-worker), all as manifest fields | No code of the skill's own in the job, so behavior matches Glue and the customer has nothing extra to maintain. The job's code is edited only for analyzer findings that can't work on a plain Ray container, with the user's approval (`SKILL.md` Step 3). The min-workers floor is kept. Refactoring to argparse plus explicit `ray.init(runtime_env=...)` is cleaner and portable, but is a code change and out of scope for this migration |
| 9 | Head pod does work (`num-cpus: 8`) or a dedicated head (`num-cpus: 0`) | DEFAULT does work (Glue parity) | Parity and lower cost. User code then shares a pod with the autoscaler sidecar and the KubeRay RBAC token. A dedicated head (`num-cpus: 0`) is safer but costs one extra node per run and no longer matches Glue's capacity |
| 10 | Object store / spilling / disk | DEFAULT from the Glue arguments; 160 GiB node ephemeral storage | Percentages become bytes of the pod limit (54Gi, not Z.2X's full 64 GB), so re-tune if the job was sized for 64 GB. `/dev/shm` counts against the pod memory limit. S3 spilling uses the same `smart_open` config Glue used, with the spill bucket access the Glue role had |
| 11 | Encryption (KMS/SSE) for output and spill buckets | ASK | Glue for Ray jobs cannot have a security configuration (CreateJob rejects it), so they relied on bucket default encryption, as the EKS pods do. Ask whether the customer wants more (bucket-default SSE-KMS); if so, grant the pod role `kms:GenerateDataKey`/`kms:Decrypt` on the key |
| 12 | IAM identity | DEFAULT IRSA, a new pod role with the Glue role's permissions | The Glue-parity boto3 (1.26.x) predates EKS Pod Identity, so the pods use IRSA. The pod role gets exactly the Glue role's permissions (parity): its managed policies attached, its other policies copied, the same permissions boundary and tags. Only statements conditioned on the Glue credential keys (`glue:CredentialIssuingService`, `glue:RoleAssumedBy`) are rewritten to act as they did for the Glue job. The skill creates a new role rather than letting the pods use the Glue role, so the Glue job and its role are never modified during the migration, the role can't be shared between Glue sessions and EKS sessions (a statement on those keys can't be right for both), and retiring the Glue role later doesn't affect EKS. The cost: grants that other resources make to the Glue role's ARN (bucket and KMS key policies, Lake Formation) must be added for the pod role; the skill lists them (`grants.md`). Narrowing the role is the customer's choice |
| 13 | Dashboard access | DEFAULT never exposed | On Glue the customer had no network path to the Ray dashboard, whose job API has no authentication in Ray 2.4. The skill keeps that: a NetworkPolicy admits only the job's own pods and the KubeRay operator's pods, and no LoadBalancer / NodePort / Ingress is created for 8265 / 10001 / 6379. The policy needs a cluster that enforces NetworkPolicies: a new cluster from the templates does; on an existing one the user confirms it. Exposing the dashboard, and securing it, is the customer's decision. During a run, `kubectl port-forward svc/<RAYJOB>-head-svc 8265:8265` reaches it without exposure; otherwise use `kubectl logs job/<RAYJOB>` and `kubectl exec <head> -c ray-head -- ray status` |
| 14 | Observability | REQUIRED; ASK which stack (default: CloudWatch Observability add-on) | Pod logs are deleted with the pods and their nodes shortly after each run, so without a log pipeline the job's output is lost. With the add-on, the driver output lands in `/aws/containerinsights/<cluster>/application` (submitter stream). Glue's `/aws-glue/ray/jobs/*` log groups and `job-result/` S3 files are replaced. Task and actor output, which Glue shipped per worker (`ray-worker-out-logs` / `ray-worker-err-logs`), is in the driver stream, complete because the manifests set `RAY_DEDUP_LOGS=0`. Alarms on Glue job states must be rebuilt on RayJob status |
| 15 | Retries, timeouts, spot | DEFAULT on-demand; `backoffLimit` = MaxRetries; `activeDeadlineSeconds` = Timeout (480 min for every Ray job; the user may choose another value) | Spot is cheaper but needs idempotent outputs (write to a run-scoped prefix, then commit) |
| 16 | Concurrency | ASK if the job ran concurrently on Glue | Each run is its own RayJob. Set the NodePool `limits.cpu` and namespace ResourceQuotas to cap the spend. A fixed-size node group needs `NumberOfWorkers` nodes per job that may run at once; otherwise later runs wait `Pending` |
| 17 | Invocation | Out of scope (flag it) | Whatever called `StartJobRun` (Step Functions, Airflow, Lambda, triggers) must create a RayJob through the Kubernetes API instead (`kubectl create -f rayjob.yaml`, or the equivalent API call) and read its status. Cleanup is automatic |
| 18 | Ownership and cost | Inform | Pricing moves from per M-DPU-second to EC2 instances + the EKS cluster fee + the Auto Mode fee + NAT gateway data processing + idle capacity. The customer now owns EKS and KubeRay upgrades, base-image CVE patching, and Ray version currency. One cluster per team amortizes this best |
| 19 | Cutover and rollback | DEFAULT shadow-run, compare, then switch | Keep the Glue job as the rollback path until the EKS job is validated |
| 20 | Autoscaler idle timeout | DEFAULT 600 s (an explicit `--auto-scaling-executor-idle-timeout` is kept), Inform | Glue's own controller managed the nodes; on EKS the Ray autoscaler removes a worker after the idle timeout, and a removed worker costs a new EC2 node plus the image pull (minutes). It also loses the objects it holds: a job that spills or has a serial phase can then run much slower than on Glue, or stall (troubleshooting `IDLE-SCALEDOWN`). The RayCluster is deleted 60 s after each run, so a longer timeout only keeps idle workers during a run. Lower it only for a job with long idle phases between bursts, where idle nodes would bill |
| 21 | Cleanup after a run | DEFAULT RayCluster 60 s after the job ends, RayJob object after a day | The RayJob's `deletionStrategy` deletes the RayCluster `--ttl-seconds` after the job ends (on success, failure or a failed submission); until then every node keeps billing. The RayJob object (no cost) stays `--keep-seconds` so its status can be read. Pod logs vanish with their nodes either way, so ship logs to the log pipeline rather than raising the TTL to keep them |
